# AI Jumpstarts: GL Coding Review and P&L Flux

Two Claude Project agents, adapted from CrossCountry's CrossCore AI Jumpstart, that run a
client's month-end close on its own NetSuite, Coupa, UKG and FP&A exports. The repo is
white-label: the same scripts and Projects serve any client, on a demo data set or on a
client's live exports.

* Current client: Unity Biomedicines (demo), `PL87 Unity Biomedicines, Inc.`
* Console 2.4.0, 2026-10-29 (`VERSION` in `src/build_pages.py`). The engines, the rulesets and
  the views version separately; the Run log shows each, and [`CHANGELOG.md`](CHANGELOG.md)
  records the changes.
* Runs every month. The committed consoles are built on Aug 2026.

## Demo and Live Data

The scripts read each export as its system writes it, finding columns by name: from
`inputs/<period>/` in the repo, or as files attached in a Project. A demo runs on a demo data
set in those formats; a live close runs on the client's own exports. The commands, the checks
and the console are the same for both. Neither engine reads a sliced or derived file, and a
client's exports and the runs built from them stay out of Git (see In Git).

## Adapting to a Client

The client is not confined to one file. Before a new client's first close, update:

| What | Where |
|---|---|
| Chart of accounts and departments, policy thresholds, vendor coding baseline | `projects/shared/client-accounts-and-departments.md`, `projects/shared/client-policy-rules.md`, `projects/gl-coding-review/client-vendor-coding-baseline.md` |
| The client, its systems and its people, as Claude is told them | Each Project's `PROJECT_INSTRUCTIONS.md`, `HOW-TO-RUN.md` and skill file |
| The entity and thresholds the scripts apply | `ENTITY`, `PREPAID_THRESHOLD` and `CAPITALIZATION_THRESHOLD` in `src/client_uc2_flux.py`; `CAPITALIZATION` and `PREPAID` in `src/client_views.py`; `CAPEX_THR` and `PREPAID_THR` in `src/build_pages.py` |
| The coding engine's policy (entity, thresholds, vendor pairs) | `src/client_uc1_engine.py` is generated by `tools/bundle_engine.py` from the `coding_engine`, `coupa_extract` and `gl_extract` packages, which are not in this repo: change them there and bundle again |
| Checks written for this client's vendors | Such as the parent's pass-through bills (`client_sources.py passthrough`, and their page in `build_pages.py`) |
| The look | `design-system/tokens.css`, `src/client_design.py`, `src/client_fonts.py` |
| Feeds the client has not sent | Header-only files in `templates/` |

File names are client-neutral (`client_*.py`, `client-*.md`), but the client's name also
appears in labels and messages across `src/`: search for it.

## Run Order: Coding Review First, Flux Last

These two sit at opposite ends of the close, and running them out of order wastes work.

1. **GL Coding Review** runs first, on the raw ledger.
   It tees up the corrections, so the accruals, prepaid and fixed-asset work in the middle of
   the close starts from a cleaner coding base.
2. The close proceeds: accruals booked, prepaids amortized, fixed assets recorded.
3. **P&L Flux** runs last, on the corrected ledger.
   It is the final check that the numbers are right, and it produces the commentary that goes
   to the senior leadership team.

Running flux on an uncorrected ledger surfaces variances that are really coding errors, so the
same item gets investigated twice. Coding Review first means fewer reclassifications to explain.

Each file lives once. `claude-projects/GL Coding Review/` and `claude-projects/P&L Flux/` show
exactly what each Project takes: `PROJECT_INSTRUCTIONS.md` to paste, and `upload/`, every file to
upload, to select all and drag in. Each is a relative symlink to its copy in `src/`,
`projects/` or `templates/`, or for NetSuite's lists to `inputs/reference/` (see
[`claude-projects/README.md`](claude-projects/README.md)).
`tools/package.py` writes them, and `make test` fails when they are out of date. It also
assembles each Project's upload folder, flat, with real copies, in `out/dist/<project>/` (and a
`.zip`): the scripts from `src/`, the Project's docs, the shared docs, its templates and
NetSuite's lists. The build runs from those folders, so what is tested is what is uploaded.

### The Console

Console 2.4.0 is laid out as Chris's August reports, in the client's design: the GL review as
Overview, Review, Confirm and Documentation; the flux pack as Executive Overview, Analysis and
Close Workflow. `build_pages.py` builds it from the run, in each Project. Each proposed Journal
Entry is filled in and editable, every vendor card shows its last three months, and the NetSuite
CSV takes the entries as edited. Published as a claude.ai Artifact, the console is in shared
mode: everyone with access sees the same review. Opened as a file, or published from an account
without the capabilities shared mode needs, it keeps the review in that browser.

`consoles/` holds one file per Project, `gl-coding-review.html` and `pl-flux.html`. Each console
version is a commit to them, tagged `console-v<version>` from 2.4.0:

```sh
git log --oneline -- consoles/
git show console-v2.4.0:consoles/pl-flux.html > pl-flux-v2.4.0.html
```

The month a console shows is only the input data it was built from (Aug 2026 for the committed
consoles).

### Working in the Repo

Python 3.9 or newer, standard library only. The console tests need Node and Playwright; the
others need only Python.

```sh
make package                  # claude-projects/ (links), and out/dist/<project>/ (copies) with .zip
make build PERIOD=aug2026     # both Projects' commands on inputs/aug2026/, from out/dist/
make test                     # claude-projects/ up to date, then the console and engine tests
```

`make build` writes `out/<period>/<project>/run.json` and the month's console, and copies the
console to `consoles/`. The console version is `VERSION` in `src/build_pages.py`. Mint a new one
only when it is agreed: add it to `CHANGELOG.md`, commit the rebuilt consoles, and tag the
commit `console-v<version>`.

### In Git

The repo is private. `.gitignore` leaves out the client's data: `inputs/`, `out/` (the runs and
local builds), the local `data/` and `status/` folders, everything in `references/` but its
README, and Office and export files (`.xls`, `.xlsx`, `.pptx`, `.docx`, `.pdf` and the like).
Chris's two August reports are kept in `docs/spec/`. The consoles in `consoles/` are committed,
every version: built with `--keep-names`, they carry the ledger, names and pay, for the
accounting team. To rebuild a month from a clone, put its exports in `inputs/<period>/` and run
`make build`. The simplest way is to link into the engagement's OneDrive data,
`7-technical-documentation/3-data/`, from the repo root (`.gitignore` leaves out `inputs`
whether it is a folder or a link). On macOS:

```sh
D="$HOME/Library/CloudStorage/OneDrive-QuantumRise/Clients - Active - Documents/<client folder>/7-technical-documentation/3-data"
mkdir -p inputs
ln -s "$D/2026-08 exports" inputs/aug2026
ln -s "$D/2026-09 exports" inputs/sep2026
ln -s "$D/netsuite reference" inputs/reference
```

`inputs/reference/` is also where `claude-projects/*/upload/` finds NetSuite's lists.

## Setup

Two Projects, one per use case. They are not combined, because the two have different
instructions, different reference material and different places in the close. Step by step,
including updating a Project that is already set up, and every file each Project takes, in
[`claude-projects/README.md`](claude-projects/README.md).

Configure once:

1. Create a Claude Project named `GL Coding Review` or `P&L Flux`.
2. Paste `PROJECT_INSTRUCTIONS.md` from `claude-projects/<Project>/` into the Project
   Instructions field. It is instructions, not an upload.
3. Open `claude-projects/<Project>/upload/`, select every file and drag them into the Project.
   NetSuite's three lists there link to the OneDrive data through `inputs/`, so set that up
   first. `make package` also puts every file, as real copies, in `out/dist/<project>/` and
   its `.zip`.
4. Add the plan workbook to the Project's files: the rolling forecast whose prior cut is the
   plan (`rolling_forecast_2026-08.xlsx` for the current client). It is client data, so it is
   not in `upload/`. It stays until the client sets a new plan.

Then each month:

5. Start a new chat in the Project for the close and attach the month's exports, as each
   system wrote them. Each `HOW-TO-RUN.md` lists them under Each Month.
6. Prompt: `Run the GL coding review for Sep 2026.` or `Run the P&L flux for Sep 2026.`

Two things to know about Project uploads. They are **flat**, so the scripts are invoked by bare
filename. And the header-only template files must be uploaded, since their presence
is how each agent detects a missing feed and reports the gap instead of quietly skipping a test.

## The Current Client: Unity Biomedicines (Demo)

What the client's data set holds, and what the agents are set for. A new client replaces this
section.

* **Entity**: one subsidiary, `PL87 Unity Biomedicines, Inc.`, on all 44,013 lines of the
  Jan 2025 to Aug 2026 ledger. There is no entity test.
* **Chart of accounts**: 7-digit hierarchical NetSuite account paths, 139 leaf accounts.
* **Departments**: ten names. 18,391 of the 44,013 lines (42%) sit in `Non-Specific`.
* **Source systems**: NetSuite, Coupa (since about Sept 2025, Prendio before it), UKG as the
  HRIS, ADP for payroll and Expensify. Adaptive Planning is unconfirmed; the plan lives in the
  rolling forecast workbook.
* **Top vendors**: Plurality Labs LLC (the parent's labs, which bill pass-through costs),
  Fisher Scientific, a partnered-research vendor, New England BioLabs and Aldevron. Corporate
  counsel is K&L Gates.
* **Thresholds**: the draft policies set $10,000 pre-close, $100,000 quarterly post-close and
  $5,000 accrual. The client set its own on 12 Oct 2026 (Mike's write-up): **$5,000** PP&E
  capitalization and **$25,000** prepaid, which the engines and the GL Coding Review's CapEx
  and Prepaid screens apply.

Two checks this ledger called for:

* **Unallocated spend review**, in GL Coding Review: the `Non-Specific` lines above.
* **Receipt-based accrual completeness**, in both agents. Coupa records goods receipts, so
  accruals are identified from what was received but not yet invoiced: about **$110K for
  Aug 2026** and **$402K for calendar 2026 to date**. A billing-pattern method (trailing
  three-month average, per the Accrued Expense Policy) is the fallback for suppliers and periods
  Coupa does not reach. Open PO commitments, ordered but *not* received (about $8.0M on calendar
  2026 POs), are reported as a disclosure and never accrued.

## Feeds

Read from the month's exports: the NetSuite Custom General Ledger, the Income Statement by month
and, for P&L Flux, the Balance Sheet; the Coupa PO lines; the rolling forecast workbook, for the
plan and for Forecast vs. Actual; and the UKG roster. The ledger is tied to the Income Statement
by account first, and a failed tie stops the run.

For the current client, the ledger runs Jan 2025 to Aug 2026, and every period's debits equal
credits to $0.00. Coupa holds calendar 2026 only, 9,571 lines and $21.1M: its 2025 tab and Open
PO report have not arrived, and without invoice-level data there is no three-way match.

Header-only in `templates/`, until the client sends real rows:

* Payroll register, the largest gap: it blocks the payroll tie-out. The UKG roster runs the
  requester flag.
* Vendor master, fixed asset register, prepaid schedule, accruals log
* External research unbilled WIP detail
* The EBITDA add-back mapping the Data Entry Policy refers to
* HRIS headcount and open purchase commitments, which the UKG roster and Coupa largely cover
* Accepted exceptions, which the reviewer fills in

`coupa_dept_code_mapping.csv` carries the Coupa department codes found so far, for the client to
confirm; until then they are read through UKG's department codes.

Both agents run with any subset present, name every absent feed in their load summary, and state
which findings are suppressed. Nothing is fabricated to fill a gap.

## Caveats Worth Carrying Into the Readout

* The client's policies in `references/` are DRAFT and unapproved. Every threshold but the
  PP&E and prepaid figures rests on them.
* The vendor coding baseline is descriptive. It records what the client does, which is not
  necessarily what it should do. It is evidence, not policy.
* For the current client, the Treasury policy found in its policy folder is CrossCountry
  Consulting's own policy, not the client's. It is excluded from both agents. See
  [`docs/DATA-MANIFEST.md`](docs/DATA-MANIFEST.md).
* Accrual estimates are pattern-derived and need controller confirmation before anything posts.
* IRC §174 output is preliminary and needs tax counsel sign-off.
